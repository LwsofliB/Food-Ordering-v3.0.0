# Food-Ordering-v3.0.0
# 多人点餐系统模拟

一个基于 Flask + 原生 JavaScript 的多人点餐演示项目，包含顾客点餐端、后厨看板、菜单管理后台三个页面，使用多进程与共享内存实现订单的异步处理与实时展示。

## 项目简介

本项目模拟餐厅点餐的完整流程：顾客在手机端浏览菜单、加入购物车并下单，订单通过进程间队列传递给后厨子进程，后厨看板定时刷新展示待做订单，厨师点击"完成出餐"后订单从看板移除。管理员可通过后台增删菜品。

项目主要用于演示前后端分离、多进程通信、共享内存、并发安全等后端工程概念，代码量小、结构清晰，适合作为学习参考。

## 功能特性

- 顾客点餐端：菜单展示、数量加减、购物车、下单取号
- 后厨看板：定时轮询待做订单、一键完成出餐、多端同步
- 菜单管理后台：添加菜品、删除菜品、菜名与价格校验
- 服务端价格校验：下单时按服务端菜单重新计价，防止前端篡改价格
- 多进程订单处理：下单接口仅入队，后厨进程异步消费并打印小票、写日志
- 共享订单状态：使用 Manager 代理对象实现主进程与子进程间的订单可见性
- 并发安全：菜单文件读写加锁、原子写替换、订单去重删除

## 技术栈

- 后端：Python 3、Flask
- 并发：multiprocessing、Manager、Queue、Lock
- 前端：原生 HTML / CSS / JavaScript，无框架依赖
- 数据存储：JSON 文件（菜单数据、订单日志）

## 环境要求

- Python 3.8 及以上
- Flask

安装依赖：

```bash
pip install flask
```

## 快速开始

1. 克隆仓库并进入目录：

```bash
git clone <仓库地址>
cd <项目目录>
```

2. 启动服务：

```bash
python server.py
```

3. 浏览器访问对应页面：

- 顾客点餐端：http://localhost:5000/order
- 后厨看板：http://localhost:5000/kitchen
- 菜单管理后台：http://localhost:5000/admin

服务默认监听 `0.0.0.0:5000`，局域网内其他设备可通过本机 IP 访问，例如 `http://192.168.1.10:5000/order`。

## 接口说明

### 页面路由

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /order | 顾客点餐页面 |
| GET | /kitchen | 后厨看板页面 |
| GET | /admin | 菜单管理页面 |

### 数据接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /api/menu | 获取当前菜单列表 |
| POST | /api/order | 提交订单，返回订单号 |
| GET | /api/kitchen/orders | 获取后厨待做订单列表 |
| POST | /api/kitchen/complete | 完成指定订单 |
| POST | /api/admin/add | 添加菜品 |
| POST | /api/admin/delete | 删除菜品 |

请求与响应均为 JSON 格式。下单接口示例请求体：

```json
{
  "dishes": [
    { "dish_name": "宫保鸡丁", "dish_amount": 2 },
    { "dish_name": "麻婆豆腐", "dish_amount": 1 }
  ]
}
```

服务端会忽略请求体中的价格字段，按当前菜单重新计价后入队。

## 实现要点

### 前后端分离

页面与数据接口通过 URL 前缀区分：`/api/*` 返回 JSON，其余路径返回 HTML 页面。前端通过 fetch 调用接口，页面可独立部署。

### 购物车状态

购物车保存在前端内存变量中，加减数量时本地计算，不发起网络请求；仅在提交订单时将完整清单发送至服务端，减少无效请求并保证交互流畅。

### 多进程订单处理

下单接口只负责校验与入队，后厨子进程从队列中阻塞读取订单，完成小票打印与日志写入。Web 请求与后厨处理解耦，避免阻塞下单响应。

### 共享订单状态

使用 `multiprocessing.Manager()` 创建的管理器进程持有真实数据结构，主进程与子进程通过代理对象访问，实现跨进程的订单可见性。活跃订单以字典形式存储，键为订单号，删除操作原子且不会误删。

### 并发安全

菜单文件的读、改、写三步操作在同一把锁内完成，避免并发修改导致数据丢失；文件写入采用临时文件加 `os.replace` 的原子替换方式，避免写入中断产生损坏文件。

### 价格校验

服务端不信任前端提交的价格，下单时以服务端菜单为准重新匹配菜品名称与价格，并对菜品是否存在、数量是否为 1 至 10 的整数进行校验。

## 已知限制

- 使用 Flask 内置开发服务器，不适合生产环境高并发场景
- 菜单与日志使用 JSON 文件存储，数据量增大后性能下降
- 后厨看板采用定时轮询，订单量大时存在请求冗余与延迟
- 订单状态保存在单机内存中，多实例部署时无法共享
- 未实现用户认证、CSRF 防护等安全机制

## 后续可优化方向

- 使用 gunicorn 或 waitress 替换开发服务器
- 将共享状态外置到 Redis，支持多 worker 与多实例部署
- 后厨看板由轮询改为 SSE 或 WebSocket 推送
- 菜单存储由 JSON 文件迁移至 SQLite 或 MySQL
- 订单号改为日期加自增序号的形式，便于顾客识别
- 购物车使用 localStorage 持久化，避免刷新丢失
